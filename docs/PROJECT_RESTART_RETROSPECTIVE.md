# 项目重启经验总结（DEMOTEST 复盘）

## 文档目的

本文件用于终止当前 DEMOTEST 后，为下一轮**从零开始的正式开发**提供统一的复盘依据与启动约束。

重点不是保留当前 demo 的具体代码，而是沉淀：

- 本轮开发中已经验证过的方向
- 本轮开发中暴露出的架构问题
- 高频报错与调试经验
- 下一轮开发必须提前约定的规则
- 建议保留的工作方式与命名规范

---

## 一、这轮 demo 的总体结论

### 1. 已验证可行的方向

本轮开发虽然终止，但以下方向已经被验证为**有价值且值得在正式版继续采用**：

1. **战斗采用地图内无缝切换，而非独立战斗场景切换**
   - 这个方向更符合项目目标。
   - 更适合后续做探索、接敌、战后恢复、点击移动、背包与道具等系统。

2. **角色本体应继续使用地图中的 CharacterBody2D 体系**
   - 不应再以独立的 `BattleUnit` 体系作为正式版主体。
   - 正确方向是：
     - 地图角色本体 = 战斗角色本体
     - 战斗能力并入地图角色
     - 后续可继续支持不同贴图、不同动画、不同职业表现

3. **底部横向技能栏是正确方向**
   - 形式参考了 Wartales / 博德之门 3 / 紫色晶石。
   - 这种布局适合正式版继续沿用。

4. **接战 / 脱离惩罚 / 近战与远程差异化设计是有效的**
   - 这些规则已经具备原型验证价值。
   - 正式版应保留，但要在更干净的架构里重做。

## 二、为什么终止当前 demo

终止原因不是单点 bug，而是**积累性问题已经超过继续修补的收益**。

### 主要原因

1. **项目中混入了过多早期遗留代码与过渡性结构**
   - 探索层、战斗层、测试层反复叠加。
   - battle_scene 路线和地图内战斗路线并存，导致职责混乱。

2. **策划方向在开发过程中发生了结构级变化**
   - 最初按独立战斗场景推进。
   - 中途明确改为地图内无缝战斗。
   - 这不是局部改动，而是承载层与对象模型的改变。

3. **临时兼容方案越来越多**
   - 为了保住已有代码，加入了大量“过渡型修法”。
   - 短期能跑，长期会降低可维护性。

4. **对象体系发生冲突**
   - `BattleUnit`
   - `MapCombatUnit`
   - 地图角色脚本
   - UI、AI、技能、TurnManager、GridManager 等均受其影响。

5. **继续在旧 demo 上修补，不如从零按正式版目标重构**
   - 当前最优解不是继续救火，而是保留经验，重新启动正式开发。

## 三、本轮开发中暴露出的核心架构问题

### 1. 战斗承载层切换过晚

最初以 `battle_scene` 为中心开发战斗，后期才改为地图内战斗。

**教训：**
- 下一轮必须在立项初期就确定：
  - 战斗是否与探索同图承载
  - 单位是否同一对象
  - 输入系统是否统一
- 这类问题不能在中期再改。

### 2. 地图角色与战斗角色双轨并存

曾经出现：
- 地图里有角色本体
- 战斗时又生成一套 `BattleUnit`
- 玩家操作的不是地图原角色，而是战斗代理对象

**教训：**
- 正式版从一开始就必须统一：
  - 地图角色本体直接进入战斗
  - 不再复制生成“另一套玩家单位”

### 3. 数据初始化过晚

进入战斗后曾出现：
- 名称全是 `Unit`
- 阵营全是 `neutral`
- `Move Range = 0`
- 敌我虽然被收集到列表，但没有真实职业与数值

**教训：**
- 正式版必须在进入战斗前完成：
  - 单位名
  - camp
  - job
  - initiative
  - HP/AP/Armor/Base Damage/Move Range
  - 技能列表
- 不能依赖默认值运行。

### 4. 地图位置与战术格系统脱节

曾经出现：
- 地图上角色有视觉位置
- 战斗网格使用另一套 origin / cell_size
- 单位进入战斗后被换算到奇怪位置
- 敌人看起来“没出现”，实际可能在屏幕外或格子外

**教训：**
- 下一轮必须尽早建立：
  - 地图坐标
  - 战术格坐标
  - 世界坐标到格坐标换算
- 这一步不能拖到太后面。

### 5. 测试场景与正式场景职责不清

`battle_scene` 既承担测试，又一度承担正式入口。

**教训：**
- 下一轮应明确：
  - `battle_scene` 如保留，只作为沙盒测试场
  - 正式流程只走地图内战斗入口

## 四、本轮遇到的典型错误与经验

下面这些问题在下一轮开发时应重点避免。

### 1. Godot 全局类解析失败

典型报错：
- `Could not parse global class ...`
- `Could not find type ... in the current scope`

高频原因：
- 脚本本身存在语法或类型错误，导致 `class_name` 注册失败。
- 一个脚本内部同时存在同名变量与同名函数。
- 某些依赖类型本身没成功解析，但在别的脚本里被静态引用。

**经验：**
- 新建 `class_name` 脚本后，先保证它能独立通过解析。
- 一旦出现这类报错，不要只看引用处，先检查被引用脚本本身。
- 在项目早期，必要时优先减少过强的静态类型依赖。

### 2. Node / Node2D 类型错配

典型问题：
- `Node` 上调用 `get_global_mouse_position()`
- Label 节点挂了 `extends Control` 或反之
- 自定义脚本假定节点结构与实际场景树不一致

**经验：**
- `Node2D` 能做的事情，不要默认 `Node` 也能做。
- 场景节点类型必须和脚本 `extends` 一致。
- 每次复制 UI 或场景结构后，必须重新核对脚本路径。

### 3. 节点路径失效

典型问题：
- `BottomSkillBar/HBoxContainer/...` 实际变成了 `BottomSkillBar/CenterContainer/HBoxContainer/...`
- UI 从 battle_scene 搬到地图内后，onready 路径仍是旧路径

**经验：**
- 一旦场景结构调整，优先先修节点路径，再修逻辑。
- 所有 UI 路径在迁移后都要逐个核对。

### 4. 共享模块静态类型过死

典型问题：
- `TurnManager.setup(units: Array[BattleUnit])`
- `GridManager.get_unit_at_grid(units: Array[BattleUnit], ...)`
- `SkillBase.can_use(user: BattleUnit, controller: BattleController)`
- UI 面板与 AI 也写死为 `BattleUnit`

后续切到 `MapCombatUnit` 后，整条链都会报类型错。

**经验：**
- 正式版的共享模块要么：
  - 以统一正式基类为中心；
  - 要么尽量采用更通用的接口约束。
- 不要让测试时期的类名渗透整个系统。

### 5. 组件接口不一致

典型问题：
- 在 `MapCombatUnit.begin_turn()` 里调用 `action.begin_turn()`
- 但 `ActionComponent` 实际只有 `reset_for_new_turn()`

**经验：**
- 组件接口必须先统一，再扩散到单位层。
- 正式版开始前应先写清楚组件接口文档。

### 6. 探索移动与战斗移动冲突

典型问题：
- 进入 combat 模式后，探索输入还在跑
- 战斗输入与探索输入同时生效
- 动画状态和位移状态互相打架

**经验：**
- 必须有明确的模式状态机：
  - exploration
  - combat
  - dialogue / result / paused 等
- 每种模式下哪些输入可用，必须硬切断。

### 7. 动画自动播放导致误判

典型问题：
- `AnimatedSprite2D.autoplay = "walk_down"`
- 实际角色没动，但一直播行走动画

**经验：**
- 角色场景中尽量不要给行走动画设 autoplay。
- 动画播放应由脚本控制，而不是场景资源自动触发。

### 8. 地图内单位只加了组，但没配真实数据

典型问题：
- 节点加了 `combat_player_unit` / `combat_enemy_unit`
- 运行时能被收集
- 但没有真实战斗数据，导致全部默认值

**经验：**
- 下一轮要区分：
  - “单位被找到”
  - “单位被正确初始化”
- 这是两件事。

## 五、这轮开发中已确认可沿用的规则与方式

以下规则建议下一轮继续沿用。

### 1. 开发协作规则

已确认应继续遵守：

1. 如果涉及先前设计或代码记忆不确定，先读取项目代码/文件，再生成方案。
2. 不直接跳到大规模实现，先确认阶段目标和承载方式。
3. 生成操作步骤时，必须细化到可直接照做。
4. 一旦架构方向改变（例如切换成地图内战斗），应先暂停继续堆功能，先重构承载层。

### 2. 场景与脚本分层思路

建议继续保持这种分层意识：

- **地图层**：地图、探索角色、交互物件、相机、触发器
- **战斗运行层**：回合、技能、AI、接战、胜负判定
- **UI 层**：技能栏、顺序条、单位信息、提示
- **数据层**：单位数据、技能数据、物品数据、任务状态、GameState

### 3. UI 方向

已验证可继续采用：

- 底部横向技能栏
- 独立的单位信息面板
- 单独的行动顺序条

### 4. 模式控制方式

建议正式版一开始就建立：

- `exploration`
- `combat`
- `dialogue`
- `result`

并约定：
- 不同模式下输入互斥
- 动画状态互斥
- UI 显示互斥

## 六、下一轮正式开发必须提前明确的设计问题

在新对话中重新开始时，以下问题必须在早期先定下来：

### 1. 战斗承载方式
- 是否完全采用地图内无缝战斗：**是**
- 是否继续保留独立 battle_scene 作为正式入口：**否**
- battle_scene 是否保留为测试场：**可保留，但仅限测试**

### 2. 单位模型
- 地图角色本体是否直接参与战斗：**是**
- 是否继续以 CharacterBody2D 角色为主体：**是**
- 是否保留独立 BattleUnit 作为正式版核心：**否**

### 3. 输入方式
- 探索是否使用鼠标点击移动：待正式版规划
- 战斗是否使用点击地面/点击目标的统一交互：建议是
- 键盘移动是否仅保留为临时调试：建议是

### 4. 地图底层战术格
- 是否需要：**必须需要**
- 是否应尽早建立：**是**
- 是否与地图真实可通行区域对齐：**是**

### 5. 数据定义方式
- 单位数据是否仍写死在脚本里：不建议
- 正式版建议：
  - 单位模板数据
  - 技能模板数据
  - 物品模板数据
  - 地图战斗配置数据

## 八、建议沿用的命名规范

下一轮建议从一开始就统一命名，避免中后期混乱。

### 1. 文件命名

统一使用：
- **脚本**：`snake_case.gd`
- **场景**：`snake_case.tscn`
- **数据文件**：`snake_case.json` / `snake_case.tres`

示例：
- `frontier_outpost_map.tscn`
- `map_combat_unit.gd`
- `combat_runtime_controller.gd`
- `turn_order_bar.gd`
- `battle_trigger_point.gd`

### 2. 类命名

统一使用：
- **PascalCase**

示例：
- `MapCombatUnit`
- `CombatRuntimeController`
- `TurnManager`
- `BattleAI`

### 3. 节点命名

场景树中的节点推荐：
- 结构层：`CombatLayer` / `CombatUI` / `Markers` / `Characters`
- 角色层：`HuChao` / `AllySpearman` / `EnemyRaider01`
- 标记点：`HuChaoBattleStart` / `EnemyRaider01BattleStart`

### 4. 组命名

统一使用：
- `combat_player_unit`
- `combat_enemy_unit`
- 如后续扩展再加入：
  - `friendly_npc`
  - `hostile_npc`
  - `interactive_container`

### 5. 资源命名建议

角色贴图、动画、音效也建议统一：
- `char_huchao_idle_down.png`
- `char_huchao_walk_down.png`
- `anim_huchao_walk.tres`
- `sfx_sword_hit_01.wav`

## 九、下一轮开发必须避免的做法

1. **不要先用 battle_scene 做太多正式逻辑，再改成地图内战斗。**
2. **不要同时维护两套正式单位体系。**
3. **不要让 UI、AI、技能、TurnManager 全部写死依赖测试类。**
4. **不要在未完成数据初始化前就开始排查“大量战斗逻辑 bug”。**
5. **不要让地图对象和战斗对象位置系统长期并存。**
6. **不要在场景资源里给角色行走动画设置 autoplay。**
7. **不要在架构尚未定型前过早堆技能和细节功能。**

---

## 十、建议保留的实用经验

1. **每阶段结束后立即做一次阶段总结。**
2. **每次结构调整后，优先先测：**
   - 场景是否能运行
   - 输入是否互斥
   - 节点路径是否仍然正确
   - 类型注册是否正常
3. **每次进入下一阶段前，先确认上一阶段不是“靠临时兼容跑起来”的。**
4. **先搭可维护的结构，再堆功能。**
5. **先搭数据流，再搭表现层。**

## 十一、给下一轮正式开发的启动建议

4. 先用一张地图做最小闭环，不要一开始铺太大范围。

## 十二、最终结论

当前 DEMOTEST 的终止是正确决定。

这轮 demo 最大的价值不在于代码本身，而在于已经明确了：

- 什么方向是对的
- 什么结构会导致后期持续返工
- 哪些错误会反复出现
- 正式版从零开始时，应该先把哪些底层问题定死

下一轮开发应以**正式版目标**为起点，而不是继续延续这个 demo 的过渡实现。
